Refine the Analyze a Document canvas design before implementation.

Do not implement into the app yet. Stay in canvas/design mode.

The current canvas direction is approved structurally, but it needs a premium refinement pass before we move to implementation.

Keep the current direction:
- premium dark UI
- document-first layout
- left document viewer + right intelligence panel
- source-backed findings
- clickable source chips / traceability
- overview-first flow before deeper tool actions
- consistent PlainPath styling

Refinement requirements:

1. Improve the Completed State first.
This is the most important screen. The user should immediately understand what the document means and what they need to do next.

Right intelligence panel should be organized in this order:
- Plain-English Summary
- Confidence / Risk Status
- Required Next Steps
- Key Deadlines
- Key Parties
- Source Traceability

Make the panel feel less crowded. Add clearer spacing, stronger section hierarchy, and more premium card structure.

2. Make the left document viewer feel more important.
On desktop, the left document viewer should take about 55–60% of the workspace width. The right intelligence panel should take about 40–45%.

The document viewer should feel like the source of truth. It should not feel like a small preview.

3. Strengthen source chip behavior.
Source chips such as “p.3 §12.1” should be treated as a signature PlainPath feature.

When clicked, a source chip should:
- scroll the left document viewer to the referenced page or section
- visually highlight the matching document section
- pulse or outline the relevant text area briefly
- keep the related finding active on the right panel

Design this behavior clearly in the canvas.

4. Refine the processing state.
Keep the processing state, but simplify the progress checklist to:
- Reading document structure
- Extracting important sections
- Checking for risks
- Generating plain-English summary

Keep it clean and professional.

5. Keep the empty upload state, but tighten the wording.
The upload state should make it clear that Analyze a Document is for reviewing existing documents, not writing new ones.

The “Works well with” examples should include:
- contracts
- lease agreements
- insurance forms
- notices
- legal or financial letters
- service agreements

6. Improve the low-confidence state.
Use clearer language:
“PlainPath could read part of this document, but the scan quality limits confidence.”

Actions should include:
- Upload clearer PDF
- Upload text-based version
- Continue with partial analysis
- Ask This Document

7. Refine mobile.
On mobile, default to the Analysis tab first, with the Document tab available beside it. The user should see answers first on mobile while still being able to inspect the source document.

8. Keep PlainPath focused.
Do not add SOP/manual builder language.
Do not add new tools.
Do not add Document Classifier or Packet Splitter.
Do not turn this into a general document-writing feature.

This tool should remain focused on:
- scanning a document
- explaining what it means
- identifying important sections
- showing risks or missing information
- giving source-backed next steps

After refining, show the updated canvas states again before implementation.
