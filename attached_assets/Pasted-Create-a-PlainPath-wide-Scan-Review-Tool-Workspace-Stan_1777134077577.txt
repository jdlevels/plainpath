Create a PlainPath-wide Scan/Review Tool Workspace Standard.

Do not redesign every tool from scratch.
Do not remove the current premium dark visual style.
Do not touch Stripe/payment behavior.
Do not start broad TypeScript cleanup.
Do not change backend analysis logic unless a UI field is already available but not surfaced.

Goal:
Standardize the structure, readability, and interaction behavior across all document scan/review tools.

Tools included:
- Analyze a Document
- Document Trust Check
- Contract Review
- Clause Extractor
- Compare Versions
- Redact Sensitive Info where applicable
- Any future scan/review tools

Problem:
The tools now look better than before, but they do not feel consistent. Some tools have clearer headers and document panels than others. Some right panels are cluttered. Some source clicks highlight clearly, while others do not. Some missing/not-found findings behave like source-backed findings even when no source exists.

PlainPath needs one consistent workspace pattern.

Required standard:

1. Shared top workspace header

Every completed tool workspace must clearly show:
- PlainPath logo / tool breadcrumb
- tool name
- uploaded file name or file names
- document type, if available
- section/page count, if available
- status pill or confidence/result status
- Save / Export / Re-analyze / New actions where relevant

The user should always know:
- what tool they are in
- what file they are reviewing
- what state the tool is in

2. Results-first header in the right panel

Each tool must have a compact results header near the top of the right panel.

The header should summarize the major findings for that tool using clickable chips/cards.

Analyze a Document:
- Summary
- Action steps
- Missing items
- Deadlines
- Risks
- Source coverage

Document Trust Check:
- Trust score
- Major concerns
- Verification steps
- Consistency checks
- Metadata/source signals
- Source coverage

Contract Review:
- Key risks
- Required next steps
- Payment/fees
- Termination/renewal
- Missing protections
- Source coverage

Clause Extractor:
- Found clauses
- Needs review
- Possible missing / not identified
- Obligations
- Dates/deadlines
- Parties/entities
- Source coverage

Compare Versions:
- Added language
- Removed language
- Modified terms
- Terms to verify
- Possible risk changes
- Source/change coverage

Redact Sensitive Info:
- Detected items
- Selected items
- Categories
- High-confidence items
- Manual items
- Export readiness

Each chip should filter, jump, or scroll the right panel to the matching section.

3. Left document panel must be dominant and readable

Every scan/review tool should keep the document panel easy to read.

Required:
- left document panel must be large enough to read
- document sections/pages must have enough spacing
- selected section must visibly highlight
- active source banner must appear when a source-backed item is selected
- tool name and file name must be visible in or above the document viewer
- no tool should leave the left side feeling blank, unidentified, or disconnected

4. Consistent source-backed behavior

For any item that exists in the document:
- clicking the right-panel item highlights that card
- clicking the source chip highlights the chip
- the left document panel scrolls to the matching section
- the matching section gets a clear violet/active border or glow
- the document shows an evidence banner with the selected source text
- inactive items remain readable but visually quieter

This rule applies across:
- Analyze action/source chips
- Trust Check concern/source chips
- Contract Review risk/source chips
- Clause Extractor clause/source chips
- Compare Versions change/source chips
- Redact selected sensitive-item chips

5. Consistent missing/not-found behavior

For findings that do not have an exact source:
- do not fake a source highlight
- do not scroll to unrelated document text
- do not show normal source-chip behavior

Instead show:
- “No exact source found”
- why PlainPath flagged it
- what sections were checked, if available
- recommended user action
- cautious wording such as “possible missing,” “not identified,” or “needs review”

This applies especially to:
- missing clauses
- possible missing protections
- unverified terms
- unclear metadata
- unavailable source sections
- low-confidence OCR findings

6. Right-panel hierarchy and clutter reduction

Across all tools:
- reduce excessive badges
- use fewer but clearer status pills
- increase body text contrast
- increase spacing between cards
- use consistent section headings
- collapse lower-priority sections by default
- keep the main decision/results sections expanded

Default expanded:
- summary/results header
- most important findings
- next steps / user actions

Default collapsed:
- source traceability
- metadata/details
- secondary tables
- lower-priority supporting information

7. Consistent loading animation

All PDF/document upload tools must use the same loading/processing animation standard.

Every processing state must show:
- tool name
- file name
- document skeleton/page preview
- animated scan/progress line
- current processing step
- right-side checklist/progress panel where applicable

No tool should show a blank loading screen or a different unrelated spinner experience.

8. Keep each tool’s identity distinct

Do not make every tool say the same thing.

The structure should be standard, but the content should remain tool-specific:

- Analyze = meaning + action plan
- Trust Check = authenticity/trust indicators
- Contract Review = contract risk/support review
- Clause Extractor = clauses, obligations, dates, parties
- Compare Versions = added/removed/modified language
- Redact = sensitive information selection and export

9. Mobile standard

All tools should use consistent mobile behavior:
- tab layout
- primary results tab first
- document tab second
- source-backed item tap can switch to document tab and highlight the source
- missing/not-found item stays in results tab and explains why flagged
- no bottom navigation should cover content
- primary action remains reachable

10. Implementation order

Do not rebuild all tools blindly.

First:
- create or document the shared PlainPath Scan/Review Workspace Standard
- identify reusable components/patterns already present
- audit each tool against the standard
- list gaps by tool

Then fix in this order:
1. shared header/tool identity
2. results-first right-panel header chips
3. source-backed highlight behavior
4. missing/not-found explanation behavior
5. right-panel readability/clutter
6. mobile consistency
7. loading animation consistency

Final report required:
A. Standard documented clearly
B. Exact tools audited
C. Gap list per tool
D. Exact files changed
E. Confirmation each tool shows tool name + file name clearly
F. Confirmation each tool has results-first header chips
G. Confirmation source-backed clicks highlight the correct document section
H. Confirmation missing/not-found items do not fake source highlights
I. Confirmation loading animation is consistent
J. Confirmation no new TypeScript/runtime errors
