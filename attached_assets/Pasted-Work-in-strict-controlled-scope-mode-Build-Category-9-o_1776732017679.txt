==================================================
GUEST IDENTITY MODEL
==================================================

Implement a server-issued anonymous guest identity.

Required behavior:
- if no demo cookie exists, server creates one
- cookie must be opaque, random, and signed or securely validated server-side
- cookie should be HttpOnly, SameSite=Lax, secure in production
- frontend must not rely on localStorage as source of truth

Recommended model:
- demo_guest_id cookie
- server stores only a hash / lookup-safe identifier

==================================================
ANTI-RESET BACKSTOP
==================================================

Need stronger protection than “cookie only”.

Implement a soft server-side backstop:
- store a fingerprint hash derived from stable low-sensitivity inputs such as:
  ip prefix + user agent
- store only the hash, not raw IP in business logic
- if guest cookie is gone but the same recent exhausted fingerprint appears,
  continue to enforce exhaustion for a defined period

Recommended exhaustion window:
- 7 days

Goal:
- prevent trivial “clear cookies and retry instantly” abuse
- do not overbuild device fingerprinting

==================================================
DB MODEL
==================================================

Use a minimal demo usage model.

Create what is needed, but recommended tables are:

1. demo_guests
- id uuid pk
- guest_hash text unique not null
- fingerprint_hash text nullable
- completed_uses int not null default 0
- exhausted_at timestamptz nullable
- first_seen_at timestamptz not null
- last_seen_at timestamptz not null

2. demo_runs
- id uuid pk
- guest_id uuid fk
- tool_key text not null
- status text not null  // started | complete | failed | blocked
- file_name text nullable
- file_size_bytes int nullable
- page_count int nullable
- created_at timestamptz not null
- completed_at timestamptz nullable
- failure_reason text nullable

Quota rule:
- maximum 2 completed uses per guest/fingerprint window

Use completed runs as the primary quota unit.
If a run fails due to server error before result generation, do not count it.
If processing begins and returns a valid result, count it.

==================================================
SERVER ENFORCEMENT
==================================================

Server must own the truth.

Required server checks on demo analyze run:
1. resolve guest from cookie
2. if none, create guest
3. compute fingerprint hash
4. load guest usage state
5. if completed_uses >= 2 OR exhausted fingerprint is detected:
   return blocked response
6. validate file type / size / page count
7. run demo analysis
8. only on success, increment completed_uses and write demo_run = complete
9. if completed_uses hits 2, set exhausted_at

Do NOT trust client-side remaining count.
