Create and preserve a standing design rule for PlainPath scan-based tools.

This is not a request to build a new tool yet. This is a product/design rule that should guide all upcoming redesigns and implementations.

PlainPath Scan Workspace Standard

For every PlainPath tool that scans, reviews, analyzes, checks, extracts, compares, or explains an uploaded document, use the same core workspace pattern:

1. Document-first layout
- The document must remain the source of truth.
- The user should always be able to see the uploaded document or document preview.
- The AI/intelligence output should explain the document, not replace it.

2. Desktop layout standard
Use a two-panel workspace by default:
- Left panel: document viewer
- Right panel: intelligence/action panel

Recommended ratio:
- Left document viewer: 55–60% width
- Right intelligence panel: 40–45% width

Both panels should support independent scrolling.

3. Mobile layout standard
Use a tabbed layout:
- Analysis tab
- Document tab

Default mobile view should open on Analysis first, with Document one tap away.

4. Source-backed findings
Every major finding should include clickable source chips when source information is available.

Examples:
- p.2 §4.1
- p.5 Termination
- p.7 Payment Terms

When a source chip is clicked:
- scroll the document viewer to the referenced page or section
- highlight the matching document area
- briefly pulse or outline the referenced section
- keep the related intelligence card active on the right panel

If exact PDF coordinates are not available:
- scroll to the closest page or text section
- highlight the nearest available block
- preserve the behavior framework for future improvement.

5. Intelligence panel standard
The right-side intelligence panel should be concise, structured, and action-oriented.

Do not display a full expanded report by default.

Default output should prioritize:
- Plain-English summary
- confidence / risk status
- top findings
- required next steps
- deadlines / dates
- key parties / terms
- source traceability

Long details should be collapsible or secondary.

6. Visual style standard
Use PlainPath’s premium dark UI language:
- calm dark background
- strong but controlled contrast
- clean cards
- clear spacing
- readable text hierarchy
- source chips as a consistent visual system

Color usage:
- purple = PlainPath intelligence/source traceability
- green = verified/confidence/safe
- amber = caution/needs review
- red = critical risk only
- blue = neutral action/help state

Avoid:
- walls of text
- dense report dumps
- excessive red/yellow warning cards
- too many borders
- tiny centered layouts on wide screens
- generic AI chat/report styling

7. Tool-specific adaptations
Use the same scan-workspace design language, but adapt the right panel to each tool.

Analyze a Document:
- plain-English summary
- risks
- missing items
- next steps
- deadlines
- key parties
- source traceability

Document Trust Check:
- trust score
- authenticity concerns
- metadata issues
- visual/document structure warnings
- fraud indicators
- confidence level
- source-backed evidence

Contract Review:
- risky clauses
- obligations
- payment terms
- termination/cancellation terms
- missing protections
- required next steps
- source-backed clause references

Clause Extractor:
- extracted clauses
- clause category
- obligation owner
- deadline/date
- risk level
- source chip
- compact table/card hybrid layout where appropriate

Compare Versions:
Use a modified version of the scan standard:
- original document viewer
- revised document viewer
- change/risk intelligence panel or drawer
- source-backed change references

Redact Sensitive Info:
Use a modified version:
- document viewer
- detected sensitive items
- redaction controls
- preview before export
- source/highlight behavior for detected items

Ask This Document:
Use the same document-first logic:
- document viewer
- question/answer intelligence panel
- every answer should include source chips when possible

Build a Contract / Document Builder:
This is not a scan tool, so it should use a related but different creation layout:
- left: live document preview
- right: builder controls/questions
- keep the premium PlainPath design language
- do not treat it exactly like a scan tool

8. Product focus rule
PlainPath should stay focused on:
- document scanning
- document meaning
- extraction
- risk review
- trust review
- source-backed explanations
- action steps

Do not add SOP/manual builder language.
Do not add generic document-writing language.
Do not add Document Classifier or Packet Splitter yet.
Do not start new tools until the current core tool redesigns are completed.

9. Implementation discipline
When implementing each redesigned tool:
- follow the approved canvas closely
- do not reinterpret it into a long report page
- do not expand every section by default
- preserve compact cards and clear hierarchy
- keep the document visible and dominant
- keep source chips functional

Please save this as the standing PlainPath Scan Workspace Standard and apply it to Analyze a Document and the upcoming core tool redesigns.
